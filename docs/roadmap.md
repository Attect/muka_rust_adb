# 实现路线

目标是兼容官方 ADB，而不是只实现一个相似命令行工具。路线按协议边界推进。

## 当前替代性评估（2026-07-20）

- 常用 host CLI、smart-socket、CNXN/AUTH、多路复用、sync、shell v2、安装、forward/reverse、mDNS pairing 和 server 生命周期已经达到可持续回归的状态。Windows 当前机器上的 Rust `adb.exe` 已替换 SDK 中的默认入口；官方二进制保留为带 `disabled` 后缀的备份，不参与测试。
- 证据门禁：Windows `cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`、库测试 464/464、bin 测试 2/2、AOSP CLI 差分 3/3、host 兼容 165/165、server runtime 4/4 全部通过；隔离 USB/mDNS 的完整 AOSP `test_adb.py` 共 21 项，其中 9 项实际通过、12 项按官方脚本条件跳过；真实 USB `PowerTest.test_resume_usb_kick` 已用 debug 和 release 构建分别通过，release 在广播后 0.339 秒内中断 shell。AOSP `test_device.py` 的默认安全门禁 20/20、tracker proto text/binary 2/2、JDWP snapshot 和 `SocketTest.test_socket_flush` 在 API 36 真机通过，socket flush 另在 API 34 通过。WSL `x86_64-unknown-linux-musl` 已产出可运行的 `static-pie` `adb`，`readelf -d` 无 `NEEDED`；`x86_64-unknown-linux-gnu` 发行物只依赖 `libgcc_s/libm/libc/ld-linux` 系统组件；两个发行目录都只有一个 `adb`。Windows x64 vendored-libusb 单文件已在 API 28/34/36 三台真机完成 `devices/get-state/get-devpath/shell` 只读回归，API 28 另有 push/pull SHA-256、forward/reverse echo、显式 zstd push/pull、server 重启以及零延迟 `detach`/`attach` 身份保持证据；Windows 32 位不在支持范围内。fastdeploy 已在 API 28/34、incremental 已在 API 36 完成真实设备回归。
- Windows x64 release `adb.exe` 的 PE 导入表已用 `llvm-objdump -p` 检查，只有 Windows 系统组件，没有 `AdbWinApi.dll`、`libusb-1.0.dll`、`VCRUNTIME140.dll` 或本项目私有 DLL；发布目录只需一个 `adb.exe`。2026-07-20 包含 smart-socket 有序关闭、AOSP help 正文和 mDNS 启动顺序修复的构建 SHA-256 为 `d2ac7a4217e012dc95a83edb37268db73bdb88ff5baee8996fed191af9a26721`；SDK 中两枚官方 `AdbWin*.dll` 已可逆改名为 `.disabled`，三台 USB 设备仍可枚举和执行 shell，证明 Rust 程序不加载它们。
- 单文件发布门禁已统一：Cargo 配置默认隔离 pkg-config，第三方 C 库走 vendored 静态源码；`scripts/build-standalone.ps1` 固定构建 Windows x64 MSVC 并检查 PE 导入，`scripts/build-standalone.sh` 为 Linux musl 构建并要求 ELF 无动态依赖，GNU/Linux 与 macOS 只允许系统运行库/框架。两个脚本都会把最终程序复制到 `target/dist/<target>/`，并要求发行目录恰好只有一个 `adb[.exe]`；PDB、rlib 和 Cargo 缓存不进入发行目录。系统 DLL、glibc、libSystem 仍是操作系统边界，不计入项目私有扩展。
- 以“当前 Windows 设备上的常用 ADB 工作流”为口径，替代度约为 85%--90%；以“所有官方平台、驱动和高级边界均可无条件替换”为口径，当前约为 70%--80%。后一个数字受未验证环境约束，不代表协议实现覆盖率。
- 尚不能宣称完全替代的硬阻塞：macOS/Linux 真机 USB 尚未验证，Windows WinUSB/第三方驱动矩阵尚未覆盖，USB 热插拔/睡眠恢复仍缺完整跨驱动实机证据，AOSP `test_device.py` 的 recovery/bootloader/真实 JDWP/APEX 组合仍缺设备回归。CNXN/AUTH 已改为先注册可取消的 `offline` pending transport，收到 TOKEN 后发布 `AUTHORIZING`，成功后原位升级，失败时清理；AOSP 虽保留 `CONNECTING` enum/protobuf 值，但当前生产源码没有 `SetConnectionState(kCsConnecting)`，不把不可观察的保留值列为独立替代缺口。Windows shell 已覆盖 AOSP 特殊键序列、Ctrl/AltGr、BMP/非 BMP 输入和 escape 断开，仍缺不同实体键盘布局、死键与复杂输入法矩阵。官方 37.0.0 独立 server 已在隔离端口验证 `LIBADBMDNS` 和新增路径字段，当前解码器可兼容；2026-09-11 又用 37.0.1 官方二进制实测 `mdns check` 文案（`adb discovery 0.0.0`）与 `LIBADBMDNS`(3)/`LIBADBUSB`(4) wire 值，`mdns check` 与 server-status 自报/解码已对齐，USB 维持 vendored libusb 的结论见 `docs/windows-usb.md`。
- 后续按优先级推进：P0 完成 WinUSB/第三方驱动与 macOS/Linux 真机矩阵；P1 扩大官方差分到 server-status、forward/reverse、shell、APEX/JDWP/recovery；P2 补充真实设备自动化、长时间运行/热插拔/睡眠恢复和发布 artifact 替换检查。每项必须同时落测试、文档和可复现命令，未有硬件证据的能力不标记为完成。

## 第三阶段：设备服务

- shell/exec/abb：shell v2 已区分 stdout、stderr、exit code，交互 pty/raw、非交互 stdin 转发、stdin packet、关闭 stdin、初始窗口尺寸和持续窗口尺寸变化已接入；v2/legacy 交互 stdin 已共享 AOSP 行首 escape 状态机，`~.` 立即打印断开提示并成功退出，legacy 普通 EOF 不 half-close；Windows raw stdin 会精确保存/恢复 console mode，通过 `ReadConsoleInputW` 转换 AOSP 特殊键、Ctrl/AltGr 和 UTF-16 输入，ConPTY/API 36 真机已验证连续交互命令、中文、非 BMP UTF-8 原始字节 `f0 9f 98 80` 与 `~.` 断开；终端型 `exec-in` 也按 AOSP `copy_to_file` 复用 raw console 输入，管道输入不变；legacy 非交互 command 不再因 host 写半关闭而提前关闭整个 ADB stream；`exec-in`/`exec-out` 已接入 `exec:` service；`abb` 已接入 `abb:` service；剩余终端工作是实体键盘布局、死键和复杂输入法矩阵，而非基础特殊键映射。
- sync：已实现 v1/v2 `ls`、`push`、`pull` 的普通文件、目录递归、空目录保留和 64 KiB 分块，v2 `STAT/LIST` 已解析保存 `dev/ino/nlink/uid/gid/atime/mtime/ctime` 扩展字段，支持单文件 `push --sync` 按 AOSP 只比较 mtime、`adb sync` 按 size/mtime、dry-run、`push -q`/`pull -q` 静默摘要、Unix host push/sync 保留符号链接、pull 跟随远端符号链接、pull 按实际接收字节完成、基础属性保留（含 v2 64 位 mtime）、目录 push best-effort mode/mtime 恢复和 Brotli/LZ4/Zstd 压缩；显式 `-z` 在 legacy 设备上按官方忽略压缩并完成 v1 传输，在 v2 设备上不按算法 feature 过度拒绝，`-z any` 才依据 feature 选择算法，缺少 dry-run feature 时返回官方 `adb: error:` 英文错误。FIFO/Unix socket 等不支持传输的特殊文件按官方输出 `adb: warning: skipping special file` 后继续，目录流程计入 skipped。压缩 pull 已按 AOSP 在 decoder frame 结束后继续消费外层 sync `DONE`，连续目录文件不会错位；`sync:` 会话成功或提前结束时按 AOSP 发送 `QUIT`；`adb sync` 已按官方 `ANDROID_PRODUCT_OUT` 分区映射同步 `data/odm/oem/product/system/system_ext/vendor`，支持 `-l`、`-n`、`-q`、`-z/-Z`。剩余 host 工作集中在错误展示和真实设备差分，而非设备端 SELinux/xattr/capabilities 设置。
- forward/reverse：已实现 host 侧 `tcp:<port>` 监听、Unix `localfilesystem:<path>` 监听、Linux `localabstract:<name>` 监听、Linux `vsock:<port>` 监听和规则管理；host forward listener 已按 AOSP 调整为 local 端点全局唯一，支持跨 transport 原地重绑定和按 local 删除，并会在 transport 关闭、手动 disconnect、offline reconnect 或同 serial transport 替换时移除关联 listener；全局 `-a` 会按 AOSP 让无显式主机名的 forward TCP listener 绑定所有 IPv4 接口，默认仍只绑定 loopback；`localreserved`、未知 socket、vsock 和 `acceptfd` 的错误/范围边界已按 `socket_spec.cpp` 对齐。legacy forward 首请求按 accept 顺序完成全局变更，forward listener accept 后恢复 blocking，避免 Windows `WouldBlock` 提前断流；remote 侧 `vsock:<CID>:<port>`、`jdwp:<pid>` 会按官方 service 字符串透传；reverse 已支持 CLI、per-transport allowlist、设备主动 `A_OPEN`，并可连接 host TCP、Unix filesystem、Linux abstract/vsock socket；`host:disconnect` 空目标和指定目标响应已按官方语义对齐。
- 已接入 jdwp、track-jdwp、track-app、logcat、bugreport、backup/restore、sideload/rescue、install/install-multiple/install-multi-package/uninstall、root/unroot、tcpip、usb、remount、verity、reconnect 等基础 service 或 shell 工作流；incremental install 已实现 `.idsig`/fs-verity、跨平台 `inc-server`、按需块传输、优先级块和 LZ4 压缩，并在 API 36 真机完成 v4 `.idsig` 基线到 incremental 更新回归；single APK fastdeploy 已实现 agent、metadata、patch、apply 和回退主流程，并通过 API 28/34 真机回归。仍需补更多平台设备和 logcat 交互细节等高阶工作流。

## 第四阶段：无线调试与配对

- 已完成：mDNS 真实发现 `_adb._tcp`、`_adb-tls-connect._tcp` 和 `_adb-tls-pairing._tcp` 服务，`host:mdns:services` 读取当前仍 active 的服务表，`host:mdns:check` 和 `server-status.mdns_enabled` 反映本 server 后端状态，`adb connect <mDNS 实例>` 会优先解析 `_adb-tls-connect._tcp`，再回退 `_adb._tcp`，并拒绝把 `_adb-tls-pairing._tcp` 当作 connect 目标；已连接实例的自然断线支持 250ms/3s/20 轮退避恢复。
- 已完成配对码 TLS pairing：`adb pair HOST[:PORT] [CODE]`、`host:pair:<code>:<host>`、显式地址/mDNS pairing 实例解析、TLS 1.3 双向证书、TLS exporter 绑定、BoringSSL 兼容 SPAKE2、AES-128-GCM PeerInfo 交换和 `adb_known_hosts.pb` 持久化。二维码配对属于图形化配对入口，不计入官方 adb CLI 替代门禁。
- 已完成 `adb connect` TCP transport 的 `A_STLS` TLS 1.3 握手、pair 成功后的同 GUID mDNS best-effort 自动连接、fresh server 状态收到已知 secure-connect 实例后的自动连接，以及已连接 mDNS 实例自然断线后的退避恢复；显式 `disconnect` 会取消当前恢复任务。server 重启逻辑已有单测覆盖，但真实无线设备重启、mDNS 事件时序和跨平台网络恢复仍缺硬件证据。
